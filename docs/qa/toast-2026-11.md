# ui-toast QA (November 2026)

Screenshots: `docs/qa/toast/`, three skins by light and dark by 360, 768
and 1280 px. Checked by `apps/playground/e2e/toast.spec.ts` in all six
skin and mode combinations, plus the shared axe, keyboard and
reduced-motion specs.

## What is asserted

| Check | Result |
|-------|--------|
| `data-placement` pins the region to each of the six corners and edges | passes |
| Default placement is bottom-end; RTL flips start and end | passes |
| The region does not block the page (`pointer-events: none`); a toast takes the pointer | passes |
| A toast inserted into a persistent live region appears; its dismiss button removes it | passes |
| `[hidden]` removes a toast | passes |
| The neutral toast keeps a visible edge | passes |
| Toast text >= 4.5:1 | passes except the upstream palette values below |
| Dismiss button: label and focus ring follow the toast's text colour | focus ring >= 3:1 on every fill (shared keyboard spec) |
| Reduced motion: the enter transition and the loading pulse stop | passes (shared motion spec) |

## Not done by CSS (documented for the consumer)

Inserting and removing toasts, auto-dismiss timers (pause on hover and
focus; never auto-dismiss errors or toasts with actions, WCAG 2.2.1), the
live region (it must already exist in the DOM before a toast is inserted),
a visible dismiss control, and keyboard access to the region. Toasts must
never take focus. There is no exit transition: CSS cannot remove a node.

## Findings

- **Dismiss button on a solid fill.** A `ui-button ui-ghost` inside a solid
  toast kept its own neutral text and focus-ring colours, so the ring
  measured about 1.4:1 on the success, danger and primary fills and, in
  shadcn, the label was dark on a dark fill (1.12:1). The shadcn adapter
  paints its ghost button's colour directly rather than through the
  `--ui-c-*` variables, so overriding variables alone did not reach it. The
  toast now sets `--ui-toast-fg` (its own text colour) and recolours the
  label, hover tint and focus ring of buttons inside it, explicitly, at a
  specificity that wins.
- **Intents never paint.** Following the alert cascade bug (see
  `accordion-2026-11.md`), intents only set variables; the base rule paints
  from them. There is no same-specificity paint conflict to depend on
  emission order, and a unit test asserts it.
- **No ghost style.** A floating toast needs an opaque background, so
  `ui-ghost` is not offered.
- **Axe on a loading toast.** The pulse lowers the opacity, so axe samples a
  blend with the page; the allow-list has one entry for `ui-toast.ui-loading`
  and its contents with that reason, and the static contrast of the loading
  toast is asserted in `toast.spec.ts`.

## Contrast exceptions (palette values, mirrored from upstream)

Solid and soft fills reuse each skin's intent pairs, so the values already
recorded in `a11y-2026-11.md` appear here:

| Skin / mode | Toast | Ratio |
|-------------|-------|-------|
| shadcn light | solid `ui-danger` | 3.60 |
| daisyUI light | `ui-soft ui-danger` | 4.47 |
| daisyUI dark | solid `ui-primary` (and loading) | 4.13 |

`toast.spec.ts` asserts this exact set, so a fix or a regression both fail;
the axe allow-list has an entry per case, each with its reason. The
neutral, outline, size and other intent toasts are >= 4.5:1 everywhere.
